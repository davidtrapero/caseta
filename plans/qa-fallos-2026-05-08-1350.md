## Categoría A — Timeout en tests multi-login o admin (20 fallos)

**Tests afectados**: ADMIN-001 a ADMIN-012, AUTH-003, AUTHZ-007, INV-003/004/005, TURNOS-001/002/007

### Diagnóstico

El fix anterior introdujo `waitForLoadState('networkidle')` en `app/tests-e2e/_helpers.ts` línea 37 para drenar el `router.refresh()` pendiente tras el login. El evento `networkidle` espera a que no haya peticiones de red durante 500ms, pero Next.js App Router hace prefetch y polling continuo de RSC que impide que esa condición se cumpla dentro del timeout de 60s. Los tests con un solo `loginUI` en páginas simples pasan porque el polling aún no ha arrancado; los que tienen doble `loginUI` (logout + segundo login) o navegan a páginas de admin con más componentes RSC fallan sistemáticamente.

### Fix

**Archivo**: `app/tests-e2e/_helpers.ts`, línea 37  
**Cambio**: `'networkidle'` → `'load'`

```diff
-  await page.waitForLoadState("networkidle");
+  await page.waitForLoadState("load");
```

El evento `load` dispara cuando el DOM y todos los recursos estáticos están listos, sin esperar al silencio de red. Es suficiente para garantizar que el redirect post-login y el RSC inicial se han completado antes de que el test interactúe con la página.

## Categoría B — Bugs de autorización en la aplicación (2 fallos)

**Tests afectados**: AUTHZ-003, AUTHZ-004

### Diagnóstico

Hay una divergencia entre la definición de roles en CLAUDE.md y la implementación actual:

**AUTHZ-003 — Gerente puede calcular nóminas**  
Archivo: `app/src/app/(app)/caja/nominas/page.tsx`, línea 38  
```ts
const puedeCalcular = user.rol === "admin" || user.rol === "gerente";
```
Según CLAUDE.md: `gerente` tiene "operativa diaria completa, sin nóminas ni usuarios". El gerente no debería poder calcular nóminas.

**AUTHZ-004 — Gerente puede acceder a la lista de usuarios**  
Archivo: `app/src/app/(app)/admin/usuarios/page.tsx`, línea 24  
```ts
const { user } = await requireRole(["admin", "gerente"]);
```
El gerente puede ver la página de usuarios (aunque `puedeEditar` se limita a admin). Según CLAUDE.md, la gestión de usuarios es exclusiva del rol `admin`.

### Estado

**Pendiente de decisión de producto.** Las opciones son:

1. **La implementación es la intención**: el spec de CLAUDE.md está desactualizado. En ese caso los tests deben actualizarse para reflejar que el gerente tiene acceso de solo lectura a usuarios y puede calcular nóminas.
2. **El spec es correcto**: los dos archivos de app tienen un bug de autorización. En ese caso:
   - `nominas/page.tsx:38` → `const puedeCalcular = user.rol === "admin";`
   - `admin/usuarios/page.tsx:24` → `requireRole(["admin"])`

No se toca código hasta que se tome la decisión.

## Categoría C — Selectores incorrectos en specs (5 fallos)

### AUTHZ-005 — Link a "Usuarios" no encontrado en sidebar

**Test usa**: `getByRole('link', { name: /usuarios/i })`

**Causa**: El sidebar principal (`app/src/app/(app)/layout.tsx`) no tiene un link directo a `/admin/usuarios`. El link al área de admin es `{ href: "/admin", label: "Administración" }`. El link "Usuarios" existe como tab dentro del layout de admin (`app/src/app/(app)/admin/layout.tsx`), no en el sidebar lateral.

**Fix**: Navegar primero a `/admin` por el sidebar y después seleccionar el tab, o usar el link de tab directamente:
```ts
// Opción A: selector del tab dentro de /admin
await page.getByRole('link', { name: 'Usuarios' }); // dentro de nav[aria-label="Secciones de administración"]

// Opción B: scope explícito al nav de tabs
await page.locator('nav[aria-label="Secciones de administración"]')
  .getByRole('link', { name: 'Usuarios' });
```

### INV-002 e INV-007 — Strict mode: "Cerveza test" aparece 2 veces

**Test usa**: `getByText('Cerveza test')`

**Causa**: La página `/inventario/movimientos` tiene un `<select id="producto">` con las opciones de productos (incluyendo `<option>Cerveza test</option>`) y además filas de tabla con el nombre del producto en `<td>`. Playwright encuentra los dos elementos y lanza error de modo estricto.

**Fix**: Acotar el selector a la celda de tabla:
```ts
// Opción A
page.getByRole('cell', { name: /Cerveza test/i })

// Opción B
page.locator('td').filter({ hasText: 'Cerveza test' }).first()
```

### TURNOS-008 — `locator('nav')` visible en `/turnos/imprimir`

**Test asume**: que no hay `<nav>` visible en la página de impresión.

**Causa**: La página `/turnos/imprimir` renderiza dentro del `AppLayout` normal, que incluye el `SidebarNav` con su elemento `<nav>`. El CSS `.no-print { display: none }` solo aplica en `@media print`; en el navegador headless de Playwright el nav está presente y visible.

**Fix**: Cambiar la aserción. En lugar de verificar ausencia de nav, verificar el contenido específico de impresión:
```ts
// En vez de:
await expect(page.locator('nav')).not.toBeVisible();

// Verificar que la tabla de impresión está presente:
await expect(page.locator('table.print-table')).toBeVisible();
// O verificar que el sidebar no contiene links de navegación de la app:
await expect(page.locator('.no-print')).toBeAttached(); // existe pero se ocultará al imprimir
```

### VOL-001 — `getByLabel(/nombre y apellidos/i)` no encontrado

**Test usa**: `getByLabel(/nombre y apellidos/i)` en `/apuntarse/<token>`

**Causa confirmada por lectura del código**: El label real en `app/src/app/apuntarse/[token]/_components/formulario-voluntario.tsx` es exactamente `"Nombre y apellidos"` (línea 68). El selector regex `/nombre y apellidos/i` debería funcionar. Las causas probables son:

1. **El token usado en el test no existe en la BD**: la página devuelve 404 o un estado de error, y el formulario no se renderiza.
2. **`clearCookies()` antes de navegar no limpia el estado de sesión** y la página redirige.

**Fix**: Verificar que el test usa un token sembrado por `resetServerDb`. El endpoint `/api/test-reset` debe devolver un `tokenVoluntario` en el seed para que la navegación cargue el formulario correctamente. Si no existe en el seed, añadirlo. El selector en sí es correcto y no necesita cambio.
